# نمط "النسخة الكاملة على الجوّال" (Desktop View)

آلية رسمية تتيح لزائر الموبايل تصفّح الموقع بواجهة سطح المكتب الكاملة (viewport=1280) بدل واجهة
الموبايل المتجاوبة، عبر زر تبديل ثابت (`MobileTopToggleBanner`)، دون التأثير على أداء أو صحّة
الموقع في وضعه الطبيعي.

## لماذا لا حلّ أبسط أولًا؟

المحاولة الأولى (قبل هذا التصميم) كانت سكربت عميل (`<script>`) يحذف وسم `<meta name="viewport">`
الذي يولّده Next.js تلقائيًّا ويعيد إنشاءه بقيمة مختلفة بعد الترطيب (hydration). ثبت بقراءة كود
React/Next.js الفعليّ (`react-dom-client.development.js`, `metadata.js`) أن هذا غير موثوق بنيويًّا:

- Next.js يرسم وسم الـviewport عبر مكوّن خادم غير متزامن (`Viewport`) مُغلَّف بحدود Suspense — توقيت
  ظهوره بالنسبة لأي سكربت عميل ليس مضمونًا (سباق حقيقي، لا افتراض).
- React لا يُوحِّد (dedupe) وسوم `<meta>` المتعددة بنفس الاسم (`getResource()` تُعيد `null` صراحةً
  لعنصري `meta`/`title` في مصدر React). فأي تكرار للوسم يبقى تكرارًا فعليًّا، لا "يُصحَّح تلقائيًّا".

النتيجة: سلوك غير حتمي عبر المتصفّحات/التوقيتات — غير مقبول لميزة طويلة الأمد.

البديل الثاني المُقترَح (`generateViewport()` مع قراءة `cookies()`) رُفض أيضًا: أي قراءة لـ`cookies()`
داخل مسار الرندر (بما فيه `generateMetadata`/`generateViewport`) تُخرِج الصفحة بأكملها من التخزين
المؤقّت الثابت لـISR — بلا Partial Prerendering مُفعَّل بهذا المشروع (لا يوجد `experimental.ppr` في
`next.config.ts`)، فلا آلية عزل متاحة تمنع ذلك. هذا القيد موثَّق بحادثتين سابقتين حقيقيتين بهذا
الكودبيس (`site-header.tsx` القديم، وكوكيز موضوع الرياضة) — كلتاهما كسرتا ISR للموقع كامل بنفس الآلية
تحديدًا.

## الحلّ المعتمَد: Middleware + Rewrite + شجرة موازية

1. **`src/middleware.ts`**: نقطة الدخول الوحيدة للمنطق. يقرأ كوكيز `acm_site_view`؛ إن كانت قيمتها
   `desktop`، يُنفِّذ `NextResponse.rewrite()` (لا `redirect()`) إلى نفس المسار تحت بادئة
   `/desktop-view/*`. الرابط الظاهر بشريط العنوان لا يتغيّر أبدًا. عدا القراءة والـrewrite، لا حالة
   ولا منطق آخر بهذا الملف عمدًا (خفيف، بلا أي اعتماديّة على الشبكة أو قاعدة بيانات).
2. **`src/app/desktop-view/layout.tsx`**: المكان الوحيد الآخر المسموح فيه بمنطق جديد. يُصدِّر حصرًا:
   ```ts
   export const viewport: Viewport = { width: 1280, initialScale: 1, userScalable: true };
   ```
   عبر Metadata API الرسمية — لا سكربت، لا DOM manipulation، ولا تُعدَّل هذه القيمة بعد الترطيب أبدًا.
3. **شجرة `src/app/desktop-view/**`**: تُطابق تمامًا بنية `(site)/`, `(sport)/`, `(reels)/` الحقيقية،
   ملفًا بملف. كل `page.tsx`/`layout.tsx`/`error.tsx`/... بها إعادة تصدير فقط:
   ```ts
   export { default, revalidate, generateMetadata, generateStaticParams } from '@/app/(site)/.../page';
   ```
   **صفر نسخ منطق** — لا Page Component، لا Layout Logic، لا Providers، لا Server Actions مُكرَّرة. أي
   تعديل مستقبلي على صفحة حقيقية ينعكس تلقائيًّا على نسختها بالـdesktop-view دون أي تعديل هنا.

   استثناءان فقط، كلاهما توجيه/قيمة تهيئة لا منطق:
   - **`error.tsx`**: يتطلّب حرفيًّا سطر `'use client'` داخل ملف الـstub نفسه (فحص Next.js البنائي على
     مستوى الملف يتجاوز إعادة التصدير — أُثبت بفشل بناء فعليّ `must be a Client Component`).
   - **`revalidate` على الصفحات ذات المعاملات الديناميكية** (`[idslug]`, `[slug]`, ...): محلّل Next.js
     البنائي (`next build`) لا يتعرّف على قيمة `revalidate` مُعاد تصديرها من ملف آخر عبر
     `export { revalidate } from '...'` تحديدًا حين تجتمع مع `generateStaticParams` — يُصدر تحذير بناء
     فعليّ (`can't recognize the exported revalidate field ... The default config will be used instead`)
     ويسقط بصمت لقيمة Next الافتراضية (تُعطِّل عمليًّا التحديث الدوري القائم على الوقت لهذه الصفحات
     تحديدًا). أُثبت تجريبيًّا ببناء إنتاج فعليّ (`next build`) طبَّق هذا على 8 صفحات
     (`articles/[idslug]`, `news/[dd]/[mm]/[yyyy]/[idslug]`, `news/live/[slug]`,
     `news/writer/[idslug]`, `radio/[slug]`, `tv/[slug]`, `reels/[idslug]`, `newspaper/[idslug]`).
     الإصلاح: تصريح رقم حرفي مباشر بملف الـstub نفسه:
     ```ts
     export const revalidate = 36000; // يُطابق الصفحة الحقيقية — تحقّق عند أي تعديل هناك
     export { default, generateStaticParams, generateMetadata } from '@/app/.../page';
     ```
     رقم واحد مُكرَّر (لا منطق) — أُعيد بناء الإنتاج بعد الإصلاح وتأكَّد اختفاء التحذير بالكامل من الـ8
     صفحات، وتحقّقت آلية ISR (رأس `x-nextjs-cache`: `HIT`) بنفس السلوك على الشجرتين.

## لماذا `/desktop-view` تحديدًا لا `/__desktop`؟

الاسم الأصلي المُقترَح كان `__desktop`. ثبت بالاختبار الحيّ المباشر (سلسلة حقيقية من 404 غير قابلة
للتفسير رغم مسح الـcache وإعادة التشغيل الكامل) أن Next.js يستثني أيّ مجلّد باسم يبدأ بشرطة سفلية
(`_`) من التوجيه كليًّا — اصطلاح "Private Folders" الرسمي، مخصَّص لملفات مساعدة تعيش داخل `app/` دون أن
تصبح مسارات. `__desktop` يبدأ بـ`_`، فكان يُستبعَد بنيويًّا من التوجيه بصرف النظر عن أي شيء آخر — لا
علاقة له بالـcache. استُبدل بـ`desktop-view` (بلا شرطة سفلية بادئة)، وهو مقطع غير محتمل التصادم مع أي
slug تصنيف/مقال حقيقي بالموقع.

## لماذا Middleware+Rewrite لا `transform: scale()` ولا MutationObserver؟

- **`transform: scale()`**: لا يُغيّر `window.innerWidth` ولا نتائج `@media` — لا يُمكن أن يُبدِّل نقاط
  توقّف Tailwind (breakpoints) الفعليّة؛ يُغيّر المظهر البصري فقط، لا التخطيط المنطقي. غير صالح.
- **`MutationObserver`**: يبقى معالجة أعراض بعد فوات الأوان (الوسم يُكتَب بقيمة خاطئة أولًا ثم
  يُصحَّح)، عرضة لنفس فئة سباقات التوقيت التي دفعت لرفض الحلّ الأصلي، ويتطلّب صيانة يدويّة (اختبار E2E
  بعد كل ترقية Next.js) لضمان استمرار توافقه مع التغييرات الداخليّة غير الموثَّقة لـReact/Next.js.
- **Middleware+Rewrite**: القرار يصير *قبل* أي رندر React بالكامل — عند الحافة (Edge)، خارج شجرة
  React كليًّا. الصفحة الناتجة تحت `/desktop-view/*` تبقى صفحة Next.js عاديّة تمامًا، ثابتة، ومخزَّنة
  عبر ISR بشكل مستقلّ — لا استثناء، لا معالجة لاحقة، لا اعتماد على سلوك داخلي غير موثَّق.

## أثر ISR

كل صفحة موبايل حقيقية الآن لها **نظيرتان** بذاكرة تخزين ISR المؤقّت: `/news/...` و
`/desktop-view/news/...` — نفس المكوّن، نفس `revalidate`، لكن إدخالان منفصلان بالكامل (Next.js يُخزِّن
حسب المسار الكامل بعد الـrewrite). هذا **مضاعفة حقيقية لحجم تخزين الـcache** لكل صفحة تُزار بكلا
الوضعين — تكلفة معماريّة مقبولة ومُتَّفَق عليها، وليست ازدواجية كودٍ (الكود نفسه صفر تكرار). لا أثر على
سرعة الاستجابة أو صحّة إعادة التحقّق (`revalidateTag`) — الوسم نفسه يُبطِل الإدخالين معًا لأنه مرتبط
بالبيانات لا بالمسار.

**تحقّق تجريبيّ**: ببناء إنتاج فعليّ (`next build && next start`)، رأس `x-nextjs-cache` استقرّ على
`HIT` لكلتا الشجرتين بعد أول طلب (بعد انتهاء إعادة التوليد بالخلفية التي تُطلقها `STALE` الأولى — وهي
حالة عاديّة لأي صفحة ISR مبنيّة مسبقًا، لا خاصّة بالـdesktop-view)، وTTFB بالإنتاج كان بنطاق مقارب جدًّا
بين الوضعين (عشرات المللي ثانية لكلا الشجرتين، بلا فارق مطّرد) — لا تراجع أداء ملحوظ.

## كيفية إضافة صفحة جديدة مستقبلًا

عند إضافة صفحة حقيقية جديدة تحت `(site)/`, `(sport)/`, أو `(reels)/`:

1. أنشئ الصفحة الحقيقية بشكلها الطبيعي (كأنّ نمط Desktop View غير موجود).
2. أنشئ ملف `page.tsx` مطابق المسار تحت `src/app/desktop-view/...` بمحتوى إعادة تصدير فقط، يحتوي
   بالضبط الأسماء المُصدَّرة فعليًّا من الصفحة الحقيقية (لا أكثر ولا أقل — تحقّق أولًا: هل تُصدِّر
   `metadata` أم `generateMetadata`؟ `revalidate` أم `dynamic`؟ هل بها `generateStaticParams`؟).
3. لا تُضِف أي منطق آخر لهذا الملف أو لأي ملف آخر تحت `desktop-view/` عدا الحالة الاستثنائية
   لملفات `error.tsx` (تتطلّب `'use client'` فقط، سطر واحد قبل إعادة التصدير).
4. لا حاجة لتعديل `middleware.ts` — الـmatcher عام ويُغطّي أي مسار جديد تلقائيًّا.
