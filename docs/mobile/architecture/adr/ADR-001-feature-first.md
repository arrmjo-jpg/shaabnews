# ADR-001: تنظيم Feature-First لا Layer-First

## القرار
`lib/` مُنظَّمة حسب الوحدة الوظيفية (`features/articles`, `features/reels`, `features/videos`,
`features/media`, `features/auth`, `features/home`, `features/settings`) — لا حسب الطبقة التقنية
(`screens/`, `models/`, `services/` مسطَّحة). داخل كل وحدة: `data/`, `domain/`, `presentation/`. قاعدة
صارمة: لا استيراد مباشر بين وحدتين، فقط عبر `core/`.

## السبب
هدف إعادة الاستخدام المستقبلي عبر مشاريع AlphaCMS أخرى يتطلّب أن تكون الوحدات (أخبار/ريلز/فيديو/
جريدة) قابلة للعزل والتفعيل/التعطيل بسهولة حسب قدرات/ترخيص كل موقع. تنظيم Layer-First يخلط كل الوحدات
في نفس المجلدات الأفقية، فيجعل عزل أو حذف وحدة كاملة لاحقًا عملية مؤلمة ومحفوفة بالمخاطر.

## البدائل المرفوضة
- **Layer-First التقليدي** (`screens/`, `blocs/`, `repositories/` مسطَّحة تحوي كل الميزات معًا) — سهل
  البداية، لكنه يخلق ترابطًا ضمنيًا بين الوحدات بمرور الوقت يصعب فكّه لاحقًا.

## الأثر
أي ميزة جديدة = مجلد واحد جديد تحت `features/`. حذف/تعطيل ميزة = حذف مجلد واحد بلا أثر جانبي على
البقية (طالما التزمت بقاعدة "لا استيراد مباشر").
