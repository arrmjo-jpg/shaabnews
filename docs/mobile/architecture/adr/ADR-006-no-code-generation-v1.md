# ADR-006: بلا Code Generation في الإصدار الأول

## القرار
صفر `build_runner` في V1. Riverpod بصيغته اليدوية (`NotifierProvider`/`AsyncNotifierProvider` مباشرة،
لا `@riverpod`). نماذج API (DTOs) بـ `fromJson`/`toJson` مكتوبة يدويًا — لا `freezed` ولا
`json_serializable` — حتى الوصول لعتبة **20+ نموذجًا** فعليًا في المشروع.

## السبب
المسؤول الحالي عن المشروع مطوّر واحد (قد ينضم آخر لاحقًا) — ليس فريقًا كبيرًا. `build_runner` يضيف:
وقت انتظار عند كل تعديل نموذج، تعارضات Merge محتملة على ملفات `.g.dart` المُولَّدة، وطبقة تصحيح أخطاء
إضافية (خطأ في الكود المُولَّد أصعب تتبّعًا من خطأ في كود مكتوب يدويًا). لعدد نماذج V1 المتوقَّع
(~6-8 حسب `01-BACKEND-CONNECTIVITY.md`)، هذه التكلفة غير مبرَّرة.

## البدائل المرفوضة
- **`freezed` + `json_serializable` + `riverpod_generator` من اليوم الأول** — المعيار الشائع في
  مشاريع Flutter الحديثة والفرق الأكبر؛ مبرَّر عند حجم نماذج/فريق أكبر، غير مبرَّر بعد عند هذا الحجم.

## الأثر
عتبة رقمية واضحة (20+ نموذج، متوقَّع عمليًا عند إضافة الجريدة الرقمية في المرحلة ٢) لإعادة النظر —
هذا **قرار مؤقت بوعي**، لا نهائي أبدي. عند بلوغ العتبة، تُعتمَد الحزمتان معًا دفعة واحدة، لا قبل ذلك.
