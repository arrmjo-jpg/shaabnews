# الشاشات المقترحة وتدفقات العمل

**هذا قسم اقتراحيّ** (بخلاف [`01-BACKEND-CONNECTIVITY.md`](01-BACKEND-CONNECTIVITY.md) الذي يوثّق
واقع الـ backend فقط) — نقطة انطلاق للنقاش، قابلة للتعديل حسب أولويات الفريق قبل البدء بالتنفيذ.

---

## ١) البنية العامة للتنقّل

```
تسجيل الدخول
  └─ الرئيسية (لوحة سريعة: عدّادات + آخر نشاط) — مبنية من permissions[] الفعلية
       ├─ الأخبار
       ├─ الريلز
       ├─ الفيديوهات
       ├─ الجريدة الرقمية (تظهر فقط إن كانت الوحدة مفعّلة — epapers/settings.enabled)
       └─ الحساب (الملف الشخصي، الجلسات النشطة، تسجيل خروج)
```

كل قسم رئيسي (وحتى كل زر داخله: نشر/حذف/رفع/إلخ) يظهر أو يختفي بناءً على الصلاحيات الفعلية من
`GET /admin/auth/me` — لا افتراضات ثابتة حسب الدور (انظر §٦ في
[`01-BACKEND-CONNECTIVITY.md`](01-BACKEND-CONNECTIVITY.md)).

---

## ٢) تسجيل الدخول والحساب

| الشاشة | الوظيفة | نقاط API |
|---|---|---|
| دخول | بريد + كلمة مرور | `POST /admin/auth/login` |
| نسيت كلمة المرور | إرسال رابط إعادة تعيين | `POST /admin/auth/forgot-password` |
| الحساب | عرض الاسم/البريد/الدور، تسجيل خروج | `GET /admin/auth/me`, `POST /admin/auth/logout` |
| الأجهزة النشطة | قائمة الجلسات (هذا الجهاز + أجهزة/متصفحات أخرى)، إبطال جهاز عن بُعد | `GET /admin/profile/sessions`, `DELETE /admin/profile/sessions/{id}` |

**قرار تصميم مطلوب:** رابط تحقّق البريد (`GET /admin/auth/email/verify/{id}/{hash}`) مصمَّم كرابط
بريد إلكتروني موقَّع يُفتح في متصفح، لا نداء API نقياً. يحتاج التطبيق قراراً: تجاهله (يُدار من المتصفح
كما هو اليوم عبر `admin-frontend`)، أو Deep Link يفتحه داخل WebView خفيف عند النقر من تطبيق البريد.

## ٣) الأخبار (Articles)

| الشاشة | الوظيفة المقترحة | ملاحظات |
|---|---|---|
| قائمة الأخبار | فلترة بالحالة/النوع/التصنيف/البحث، سحب للتحديث، ترقيم صفحات | `GET /articles` |
| تفصيل خبر | عرض كامل + معاينة SEO | `GET /articles/{id}`, `/preview` |
| تعديل سريع | عنوان/موجز/تصنيف/أعلام عرض (عاجل/مثبّت/مميّز) — **بدون محرر نصوص غني كامل في MVP** | `PUT /articles/{id}` |
| سير عمل النشر | أزرار انتقال حالة (إرسال للمراجعة/نشر/جدولة/رفض/أرشفة) — الأزرار الظاهرة تعتمد على الصلاحية + الحالة الحالية، لا قائمة ثابتة | `PATCH /articles/{id}/status` |
| وسائط الخبر | رفع صورة غلاف/معرض من الهاتف مباشرة (كاميرا أو مكتبة الصور) | تدفّق الرفع في §٣ من `01-BACKEND-CONNECTIVITY.md` ثم `POST /articles/{id}/media` |
| التغطية الحية | عرض/إضافة تحديثات لخبر `type=live` فقط | `/articles/{id}/live-updates/*` |

**قرار منتج مقترح للمناقشة:** كتابة مقال طويل بمحرر بلوكات كامل (مطابق لـ Tiptap في `admin-frontend`)
تجربة ضعيفة على شاشة هاتف. الاقتراح: التطبيق يخدم **المتابعة والتعديل السريع والنشر**، لا الكتابة
الأولى للمقال — تلك تبقى على لوحة التحكم (ويب). يمكن تبسيطها لاحقاً بمحرر Markdown/نص خفيف إن رغب
الفريق (مرحلة لاحقة، ليست MVP).

## ٤) الريلز (Reels)

| الشاشة | الوظيفة المقترحة | ملاحظات |
|---|---|---|
| قائمة الريلز | فلترة بالحالة/اللغة، معاينة صورة الغلاف/المدة | `GET /reels` |
| إضافة ريل | اختيار فيديو من الهاتف → رفع → انتظار المعالجة → عنوان/وصف → حفظ | تدفّق الرفع إلزامي *قبل* الإنشاء (§٢.٢ في `01-BACKEND-CONNECTIVITY.md`) |
| تعديل/نشر ريل | تعديل بيانات وصفية، انتقال حالة | `PUT /reels/{id}`, `PATCH /reels/{id}/status` |

**سيناريو طبيعي جداً للموبايل تحديداً:** تصوير مقطع قصير بالهاتف مباشرة ثم رفعه كريل من نفس الجلسة —
يستحق أولوية عالية في الـ MVP لأنه أحد أقوى أسباب وجود تطبيق موبايل أصلاً (لا يحتاج نقل الملف لجهاز آخر).

## ٥) الفيديوهات (Videos)

| الشاشة | الوظيفة المقترحة | ملاحظات |
|---|---|---|
| قائمة الفيديوهات | فلترة بالحالة/الظهور/المصدر/التصنيف | `GET /videos` |
| إضافة فيديو | خياران: رفع ملف (نفس تدفّق الريل) **أو** لصق رابط خارجي (YouTube/Vimeo/MP4 مباشر) بلا رفع إطلاقاً | `source_url` مسار أخفّ بكثير للموبايل — يستحق أولوية في MVP |
| تعديل/نشر فيديو | بيانات وصفية، تصنيف، انتقال حالة | `PUT /videos/{id}`, `PATCH /videos/{id}/status` |
| لوحة الفيديو | عدّادات + فيديوهات تعثّرت معالجتها + طابور نشر متأخّر | `GET /videos/dashboard`, `/operations` — **مصمَّمة أصلاً في الـ backend لتُستهلك من الموبايل** (تعليق صريح في الكود) |
| تصنيفات/قوائم تشغيل | CRUD + إعادة ترتيب | اختياري لـ MVP — تأجيل لمرحلة لاحقة |

## ٦) الجريدة الرقمية (Epaper)

| الشاشة | الوظيفة المقترحة | ملاحظات |
|---|---|---|
| قائمة الأعداد | فلترة بالحالة/التاريخ | `GET /epapers` — تظهر فقط إن `epapers/settings.enabled = true` |
| إضافة عدد | رقم/عنوان/تاريخ نشر + رفع PDF (~حتى 100 ميجابايت) | رفع كبير من شبكة موبايل — يحتاج شريط تقدّم + استئناف/إعادة محاولة، انظر §٢ في `03-TECHNICAL-CONSIDERATIONS-AND-GAPS.md` |
| تفصيل عدد | معاينة الغلاف، استبدال PDF، تعيين غلاف يدوي | `POST /{id}/replace-pdf`, `POST /{id}/cover` |
| نشر/جدولة عدد | انتقال حالة (draft→scheduled→published→archived) | `PATCH /epapers/{id}/status` |
| تحليلات القارئ | عدد الفتحات/الجلسات/الصفحات الأكثر قراءة | `GET /epapers/{id}/analytics`, `/epapers/analytics` (لوحة عابرة للأعداد) |

**ملاحظة:** OCR/بحث نصّي داخل الجريدة **خارج نطاق تطبيق الموبايل V1 بقرار منتج نهائي** — لا تُبنَ شاشة
"بحث داخل PDF"، ولا أي زر/حالة متعلقة بـ OCR أو Text Layer أو Page Count. "معاينة" العدد في هذا
التطبيق تعني فتح `pdf_url` مباشرة، وليس نظام Preview مخصَّص. تفصيل كامل في
[`03-TECHNICAL-CONSIDERATIONS-AND-GAPS.md`](03-TECHNICAL-CONSIDERATIONS-AND-GAPS.md) §٣.

## ٧) تدفّقات مشتركة تستحق تصميماً موحّداً عبر الأقسام الأربعة

- **رفع الوسائط بحالة معالجة**: نفس الـ widget (اختيار ملف → شريط رفع → "جارٍ المعالجة" مع استطلاع
  دوري → جاهز) يُعاد استخدامه لغلاف الخبر، فيديو الريل، فيديو المكتبة، وPDF الجريدة.
- **بطاقة "الأزرار حسب الصلاحية"**: مكوّن واحد يقرأ `permissions[]` مرة عند الدخول ويقرر ما يُعرض من
  أزرار الحذف/النشر/الأرشفة في كل الشاشات الأربع، بدل تكرار المنطق أربع مرات.
- **تنبيه انتهاء الجلسة**: معالج موحّد لأي استجابة `401` يعيد المستخدم لشاشة الدخول (لا Refresh Token
  متاح — انظر §١ في `01-BACKEND-CONNECTIVITY.md`).
