تعديل عليه لاحقًا قرار واعٍ منفصل، لا تحديثًا روتينيًا.

## ١) Architecture

### State Management — ✅ Required: `flutter_riverpod` (يشمل `riverpod` كـ dependency)
- **آخر إصدار:** 3.4.2 (نُشر قبل 3 أيام من الفحص — نشاط ممتاز).
- **لماذا نحتاجه:** تطبيق قائم بالكامل على بيانات غير متزامنة من API (Article/Reel/Video/Media
  states) + حاجة DI حقيقية عبر الطبقات (Repository → UseCase → UI). Riverpod يوحّد الاثنين بدون
  حزمة DI منفصلة.
- **البدائل:** `flutter_bloc` (v9.1.1، 8,060 إعجاب، "Flutter Favorite" — أقوى انضباطًا لفرق كبيرة،
  لكن boilerplate أثقل لا يبرَّر لمطوّر واحد/فريق صغير كما وثّقنا في `06-...md` §٧). `provider`
  (v6.1.5+1، 11k إعجاب — أبسط لكنه فعليًا سلف Riverpod من نفس المطوّر، ولا مبرر لاختيار السلف على
  الخلف الرسمي في مشروع جديد).
- **لماذا اخترته:** يحقق أعلى قيمة لأقل تعقيد ضمن قيد "فريق صغير" الصريح في المتطلبات — تصميم واحد
  يغطي State + DI معًا، اختبار سهل، async-first يطابق طبيعة تطبيق API-محور بالكامل.
- **مجتمع قوي؟** نعم — `riverpod` الأساسي: 4,020 إعجاب/160 نقطة pub؛ `flutter_riverpod`: 2.9k
  إعجاب/140 نقطة.
- **صيانة جيدة؟** ممتازة — إصدار قبل 3 أيام فقط من الفحص.
- **يدعم Flutter 3.44/Dart 3.12؟** لم يظهر قيد SDK صريح في صفحة pub.dev المفحوصة، لكن حداثة
  الإصدار (بنفس شهر الفحص) تجعل التوافق شبه مؤكَّد — تحقّق برقم القيد الدقيق عند `flutter pub add`
  (يرفض تلقائيًا أي تعارض).

### DI — ❌ لا حزمة منفصلة (Rejected: `get_it`)
Riverpod نفسه **هو** آلية الـ DI (شجرة Providers = حاوية حقن اعتماديات). إضافة `get_it` بجانبه تعني
نظامي DI متنافسين لنفس الغرض — تعقيد بلا فائدة لفريق صغير. **لو اختير `flutter_bloc` بدل Riverpod
مستقبلاً، عندها `get_it` (v9.2.1، 4,710 إعجاب، صيانة ممتازة) يصبح الخيار الصحيح** — لكن هذا غير
معمول به هنا.

### Routing — ✅ Required: `go_router`
- **آخر إصدار:** 17.3.0 (منذ 59 يومًا). حزمة رسمية من فريق Flutter نفسه.
- **لماذا نحتاجه:** تنقّل معياري (Bottom Nav محتمل + عدة Stacks لكل قسم) + Deep Linking لاحقًا عند
  فتح إشعار (`03-NOTIFICATIONS.md`) — يفتح مباشرة شاشة المحتوى المرتبط.
- **البديل:** `auto_route` (v11.1.0، 3.4k إعجاب) — قوي لكنه يضيف طبقة Code Generation (`build_runner`)
  لميزات تشعّب تنقّل متقدمة **لا يحتاجها** حجم هذا التطبيق (بضع شاشات لكل قسم، لا تعشيش عميق). إضافة
  codegen بلا حاجة فعلية تتعارض مع "أقل عدد ممكن من الحزم".
- **لماذا اخترته:** رسمي، ناضج ("feature-complete" بحسب فريقه — أي مستقر لا مهجور)، يتكامل بسلاسة
  مع Riverpod عبر `refreshListenable`.
- **مجتمع قوي/صيانة جيدة؟** نعم — 5.76k إعجاب/150 نقطة، فريق Flutter الرسمي.
- **التوافق؟** يُتحقَّق تلقائيًا عبر `flutter pub add` — لا إشارة لأي تعارض.

### Repository Pattern — ✅ لا حزمة (Dart عادي)
هذا نمط تصميم (Interface + Implementation)، لا مكتبة. تُكتَب كصفوف Dart مجردة عادية تُغلِّف نداءات
`dio` خلف عقود نظيفة لكل Feature (`ArticleRepository`, `ReelRepository`...). **لا حزمة تُضاف هنا —
Dart يوفّر هذا بشكل كامل عبر `abstract class`.**

### Result Pattern — ✅ موصى به: **بلا حزمة** (Dart 3 sealed classes)، بديل خفيف: `result_dart`
- **التوصية الأساسية:** Dart 3.12 يدعم `sealed class` + `switch` pattern matching بشكل كامل — بناء
  `sealed class Result<T> { }` مع `Success<T>`/`Failure<T>` يستغرق ~15 سطرًا، بلا أي تبعية خارجية،
  ويُكتَب مرة واحدة فقط في المشروع. هذا يطابق تعليمة "إذا وفّرت Flutter/Dart شيئًا بشكل جيد فلا تضف
  Package له" حرفيًا.
- **إن فُضِّلت حزمة جاهزة بدل الكتابة اليدوية:** `result_dart` (v2.2.0، ~4 أشهر، 175 إعجاب، 160
  نقطة pub) — خفيفة، مصمَّمة لهذا الغرض تحديدًا (لا Functional Programming ثقيل)، تدعم `.fold()`/
  `.map()`. **Optional** لا Required — الحل اليدوي كافٍ تمامًا.
- **❌ Rejected: `fpdart`** (v1.2.0، 1.1k إعجاب) — مكتبة Functional Programming كاملة (Option/Either/
  Task/Reader...) — قوة زائدة عن حاجة تطبيق لا يحتاج Monad transformers أو Lenses؛ منحنى تعلّم غير
  مبرَّر لمطوّر واحد.
- **❌ Rejected: `dartz`** (v0.10.1، **نُشر قبل ~4 سنوات** — تحقّقت مباشرة، لا تحديثات حديثة، المجتمع
  انتقل عمليًا لـ `fpdart`) — خطر صيانة حقيقي وموثَّق، لا يوجد مبرر لاختياره على البدائل الأحدث.
- **ملاحظة إضافية — `equatable`:** أُشير إليها كتفضيل شخصي (تُنظّف مقارنة الكائنات `==`/`hashCode`
  يدويًا، مفيدة حتى مع Riverpod لموديلات الحالة). **لم تُدرَج ضمن القائمة النهائية الرسمية المعتمَدة**
  (لا Required ولا Recommended رسميًا) — تبقى خيارًا مفتوحًا يُقرَّر وقت التنفيذ الفعلي بلا التزام
  مسبق هنا.

## ٢) Networking

### HTTP Client — ✅ Required: `dio`
- **آخر إصدار:** 5.11.0 (منذ 7 أيام، نشاط ممتاز). 8,340 إعجاب/160 نقطة.
- **لماذا نحتاجه:** الباك إند يتطلب: رفع Multipart (صور/فيديو/PDF)، Interceptors (إرفاق Bearer
  token تلقائيًا على كل طلب لـ `/admin/*`، معالجة موحّدة لـ 401)، تتبّع تقدّم الرفع (شريط تقدّم إلزامي
  لملفات كبيرة حسب `02-MEDIA-AND-CONNECTIVITY.md`)، وCancel Tokens. كل هذا مدمج في `dio` جاهزًا.
- **البديل:** حزمة `http` الرسمية من فريق Dart (v1.6.0، 8.46k إعجاب) — أبسط وأخف، لكنها لا توفر
  Interceptors ولا تتبّع تقدّم الرفع أصلاً؛ إعادة بنائها يدويًا فوق `http` تعني كتابة نفس الشيء الذي
  يوفّره `dio` جاهزًا ومُختبَرًا — لا يصح رفض حزمة توفّر حاجة فعلية موثّقة بدقة (رفع الملفات الكبيرة
  هو "أهم جزء في التطبيق" حسب النقاش السابق).
- **مجتمع/صيانة؟** ممتازة على كل المقاييس.
- **التوافق؟** يُتحقَّق تلقائيًا عند الإضافة؛ لا إشارة لأي مشكلة.

### Retry — ❌ Rejected: `dio_smart_retry` — **قرار مُعتمَد: Interceptor مخصّص بدلاً منه**
**سبب الرفض ليس جودة الحزمة — بل أن إعادة المحاولة عندنا محكومة بقواعد أعمال خاصة (Business Rules)
لا تعرفها أي حزمة عامة:**

| الحالة | القرار |
|---|---|
| `401` | لا إعادة محاولة (توكن غير صالح — إعادة المحاولة عبثية، يجب تسجيل خروج فوري) |
| `500` | قد يُعاد المحاولة (خطأ خادم مؤقت محتمل) |
| `429` | ينتظر (Backoff) ثم يُعاد المحاولة — لا إعادة فورية |
| `Timeout` | يُعاد المحاولة |
| طلبات **الرفع (Upload)** | **لا إعادة محاولة تلقائية أبدًا** — إعادة رفع ملف كبير جزئيًا قد يُنتج تكرارًا أو تلفًا؛ يُترك القرار للمستخدم (زر "إعادة المحاولة" صريح في الواجهة، لا تلقائي صامت) |

هذا المنطق يُكتَب كـ `Interceptor` واحد مخصّص فوق `dio` (~30-40 سطرًا)، أدق وأكثر أمانًا من أي حزمة
عامة لا تفرّق بين هذه الحالات افتراضيًا. **لا حزمة تُضاف لهذا الغرض.**

### Logging (للمطوّر، Dev-only) — ✅ Recommended: `logger`
- **الفرق عن `dio`'s `LogInterceptor`:** ذاك مخصّص لتسجيل طلبات/استجابات HTTP فقط. `logger` أوسع
  نطاقًا — تسجيل عام منظَّم لأي حدث في التطبيق (أخطاء، انتقالات حالة، تشخيص) بمستويات (debug/info/
  warning/error) وتنسيق مقروء في Console أثناء التطوير.
- **قيد صريح:** للمطوّر فقط — **يُعطَّل/يُزال فعليًا في بناء Release** (عبر `kDebugMode` أو ما
  يعادله)، لا يظهر أي أثر منه للمستخدم النهائي أو في نسخة الإنتاج.
- `pretty_dio_logger` (v1.4.0، ~سنتان، 919 إعجاب) يبقى **Optional** إضافيًا فقط لتنسيق أجمل تحديدًا
  لسجلات HTTP إن احتاج المطوّر تفصيلاً أعمق من `LogInterceptor` المدمج في `dio`.

### Interceptors — ✅ لا حزمة (آلية مدمجة في `dio`)
`Interceptor` هو مفهوم داخل `dio` ذاته (نستخدمه لإرفاق التوكن ومعالجة 401 مركزيًا) — ليس حزمة منفصلة.

### Connectivity — ✅ Required: `connectivity_plus`
- **آخر إصدار:** 7.3.1 (منذ 8 أيام). **قيد SDK مؤكَّد صراحة من الصفحة:** `Flutter >=3.19.0; Dart
  >=3.3.0 <4.0.0` — متوافق تمامًا مع Flutter 3.44/Dart 3.12.2. 4,080 إعجاب/160 نقطة.
- **لماذا:** كشف حالة الاتصال لتفعيل منطق إعادة المحاولة/الاستكمال الذكي — متطلب مباشر.

## ٣) Security

### Secure Storage — ✅ Required: `flutter_secure_storage`
- **آخر إصدار:** 10.3.1 (~شهرين). 4.47k إعجاب/150 نقطة.
- **لماذا:** متطلب V1 صريح — "تخزين التوكن بطريقة آمنة" (`04-SECURITY.md`) عبر Keychain (iOS) /
  Keystore-backed EncryptedSharedPreferences (Android).
- **البديل:** كتابة Platform Channels يدويًا — إعادة اختراع حل أمني حسّاس ومُختبَر جيدًا؛ غير مبرَّر.

### Local Authentication — ✅ Required: `local_auth`
- **آخر إصدار:** 3.0.2 (منذ 23 يومًا)، حزمة flutter.dev رسمية موثَّقة. 3.37k إعجاب/160 نقطة.
  الحد الأدنى المعلَن: Android SDK 24+ / iOS 13+ — **مطابق تمامًا** لـ `minSdk=24` في المشروع الحالي.
- **لماذا:** متطلب V1 صريح — قفل بصمة/PIN (`04-SECURITY.md`). لا بديل جدّي يستحق الذكر — هذه الحزمة
  الرسمية المعتمَدة من Flutter نفسها لهذا الغرض تحديدًا.

### Encryption — ✅ لا حزمة إضافية في V1
`flutter_secure_storage` يغطي التشفير عند الراحة للسر الوحيد المهم (التوكن). لا قاعدة بيانات محلية
في V1 (`02-...md` §٦ — ليس Offline-First)، فلا حاجة فعلية لتشفير إضافي الآن. **Optional مستقبلاً**
فقط إن أُضيفت قاعدة بيانات محلية حقيقية.

## ٤) Storage

### Preferences — ✅ Required: `shared_preferences`
- **آخر إصدار:** 2.5.5 (~4 أشهر)، حزمة Flutter رسمية. 10.6k إعجاب/160 نقطة.
- **لماذا:** تخزين تفضيلات بسيطة (لغة، وضع ليلي، تفعيل قفل البصمة) — مطابق تمامًا لمتطلبات شاشة
  الإعدادات (`05-...md` §٥).
- **ملاحظة تقنية من الفحص:** الـ API القديم (`SharedPreferences.getInstance()`) مُعلَّم على صفحة
  الحزمة كمرشَّح للإهمال مستقبلاً لصالح `SharedPreferencesAsync`/`WithCache` — استخدم الـ API الأحدث
  من البداية (نفس الحزمة، توصية استخدام فقط، لا تغيير في القرار).

### Cache (صور الشبكة) — ✅ Recommended: `cached_network_image`
- **آخر إصدار:** 3.4.1 (~23 شهرًا — الأقدم نسبيًا، لكن المحرّك الذي تعتمد عليه `flutter_cache_manager`
  محدَّث فعليًا منذ 10 أيام فقط، فالثبات النسبي للـ wrapper نفسه ليس إشارة إهمال). 6.96k إعجاب/150
  نقطة، ~2.95M تحميل.
- **لماذا:** شاشات القوائم (أخبار/ريلز/فيديوهات) تعرض صور مصغّرة متكررة — تخزين مؤقت على القرص يقلّل
  إعادة التحميل على شبكة ضعيفة (سيناريو ميداني أساسي حسب المتطلبات).
- **سبب تثبيتها Recommended لا Required (قرار صاحب المنتج):** الصور تُعالَج وتُحسَّن أصلاً من جهة
  الـ Next.js/Backend (تحويلات/أحجام مشتقّة جاهزة — راجع `MediaConversions` في الباك إند)، وتطبيق
  الإدارة **لا يعرض آلاف الصور** كما يفعل تطبيق قرّاء عام — حجم الاستخدام الفعلي هنا أقل بكثير، فالحاجة
  حقيقية لكن ليست حرجة لإطلاق V1.

### Local Database — ✅ لا حاجة في V1 (مؤجَّل بالكامل، اختيار متعمَّد)
مطابق تمامًا لـ `02-MEDIA-AND-CONNECTIVITY.md` §٦: **ليس Offline-First**. لا داعي لأي قاعدة بيانات
محلية الآن. **عند الحاجة الفعلية مستقبلاً (لو تطوّر النطاق لمزامنة أوفلاين حقيقية):**
- **الأنسب حينها: `drift`** (v2.34.3، منذ 4 أيام، 2.4k إعجاب/160 نقطة، يوصَف بـ"مُختبَر ومُجهَّز
  للإنتاج") — الخيار الأصحّ صيانةً بين كل بدائل قواعد البيانات المحلية اليوم.
- **❌ Rejected صراحة: `hive`/`isar` الأصليتان.** تحقّقت عبر بحث ويب مباشر: مستودع `isar` الأصلي على
  GitHub **أُرشِف فعليًا (مارس 2026)** — المطوّر الأصلي تخلّى عن المشروع. `hive` الأصلية في وضع مشابه
  من التوقف الفعلي. البديلان المجتمعيان (`hive_ce`, `isar_community`) يعملان لكنهما صيانة تطوّعية
  بمخاطر معروفة (توثيق `isar_community` نفسه يصف نفسه بـ"إصلاحات أخطاء بسيطة فقط"). **لا يستحقان
  المخاطرة لمشروع جديد اليوم في ظل وجود `drift` الأكثر صحة.**
- `sqflite` (v2.4.3) يبقى بديلًا منخفض المستوى صالحًا لكن `drift` يبنى فوقه أصلاً ويضيف طبقة Type-Safe
  Query Builder — لا داعٍ لاختيار `sqflite` مباشرة لو احتجنا قاعدة بيانات لاحقًا.

## ٥) Media

### Camera + Gallery + Video Selection — ✅ Required: `image_picker`

### الضغط والتحويل — الصور: ✅ Required، الفيديو: ⚠ يحتاج قرارًا تقنيًا قصيرًا قبل الالتزام

**الصور — `flutter_image_compress` (Required):**
- **آخر إصدار:** 2.5.1 (منذ 7 أيام). 1.82k إعجاب/150 نقطة.
- **لماذا:** ينفّذ حرفيًا متطلب `02-MEDIA-AND-CONNECTIVITY.md` §٢ — تحويل `HEIC→JPEG` وضغط ذكي قبل
  الرفع، معالجة أصلية سريعة (Kotlin/Swift native)، بلا أي عمل يدوي إضافي.

**الفيديو — ⚠ أهم نقطة خطر في هذا التقرير بالكامل، تحتاج قرارك أنت لا اختيارًا آليًا مني:**

الباك إند يقبل فقط `video/mp4` و`video/webm` (`01-BACKEND-CONNECTIVITY.md` §٣) — أي فيديو MOV من
آيفون **يجب تحويله على الجهاز** (`02-...md` §٢). لكن المشهد التقني هنا غير مستقر فعليًا اليوم:
- **الحزمة المعيارية السابقة `ffmpeg_kit_flutter` مُتوقَّفة رسميًا** — تحققت عبر بحث ويب مباشر:
  الشركة المطوِّرة (Arthenica) أعلنت تقاعدها نهائيًا في **6 يناير 2025**، بلا أي تحديثات قادمة.
  صفحتها على pub.dev تحمل شارة "discontinued" صريحة. **لا يجوز اختيارها لمشروع جديد.**
- `video_compress` (v3.1.4، ~17 شهرًا بلا تحديث) و`light_compressor` (سنتان، ناشر غير موثَّق، 160
  إعجاب فقط) — كلاهما إشارات صيانة ضعيفة.
- البديل الأنشط حاليًا: **`ffmpeg_kit_flutter_new`** (fork مجتمعي نشِط، v4.6.2، **نُشر قبل يومين فقط**
  من الفحص، 160 نقطة pub، يدعم Android/iOS/macOS/Windows/Linux) — لكن حداثته الشديدة (يومان فقط)
  تعني سجل استقرار غير مُختبَر بعد فعليًا.

**توصيتي:** لا تلتزم بحزمة الآن — نفّذ **Spike تقني قصير** (يوم عمل واحد تقريبًا) قبل V1 لتحديد: هل
غالبية فيديوهات iPhone فعليًا بحاجة **Transcode كامل** (تغيير الترميز)، أم يكفي **Remux** أخف بكثير
(نقل الحاوية من MOV إلى MP4 دون إعادة ترميز الفيديو نفسه، ممكن غالبًا لأن كليهما H.264/AAC عادةً)؟
لو كفى الـ Remux، الحل أخف وأقل مخاطرة بكثير من أي حزمة Transcode كاملة. **إن احتجت الحسم الآن بلا
انتظار:** `ffmpeg_kit_flutter_new` هو الخيار الأنشط صيانةً المتاح اليوم، لكن يُستخدَم بوعي بمخاطرة
حداثته.

### الرفع (Upload) — ✅ لا حزمة إضافية (يغطيه `dio`)
`dio` يوفّر `FormData` (Multipart) + `onSendProgress` (شريط تقدّم) + `CancelToken` — كل ما يلزم
لمتطلب الرفع. **حزم رفع خلفي متخصصة** (مثل `flutter_uploader`/`background_downloader` لمواصلة الرفع
حتى بعد إغلاق التطبيق بالكامل) — **غير مطلوبة**، لأن استئناف الرفع بعد الإغلاق الكامل مستبعد صراحة من
V1 (`02-...md` §٤: "ليس متطلبًا للإصدار الأول"). **Optional/مستقبلي فقط.**

## ٧) Localization

### RTL ودعم Widgets — ✅ لا حزمة (من SDK Flutter نفسه: `flutter_localizations`)
`flutter_localizations` جزء من SDK Flutter مباشرة (`sdk: flutter_localizations` في pubspec، لا رقم
إصدار pub.dev منفصل) — يوفّر ترجمات مكوّنات Material/Cupertino + دعم الاتجاه الثنائي (RTL) بالكامل عبر

### إدارة نصوص الواجهة (Runtime Language Switching) — ❌ Rejected: `easy_localization` — **قرار مُعتمَد: `gen-l10n` الرسمي**
**قرار صاحب المنتج النهائي:** استخدام `flutter gen-l10n` الرسمي (ملفات ARB + `intl`، مدمج في SDK
Flutter نفسه، أمر `flutter gen-l10n` يُشغَّل تلقائيًا مع كل بناء) **بدل** أي حزمة ترجمة خارجية —
`easy_localization` (v3.0.8) و`slang` (v4.18.0) كلاهما **مرفوضان** لنفس السبب:
- **رسمي** — لا اعتماد على صيانة طرف ثالث لميزة أساسية طويلة العمر في المشروع.
- **أخف** — بلا أي `pubspec.yaml` dependency إضافية.
- **مناسب لمشروع طويل الأمد** — يبقى مدعومًا بضمان دورة إصدار Flutter نفسها.

**ملاحظة توثيقية (كانت مبرِّر توصيتي السابقة، والقرار الآن تجاوزها بوعي):** `gen-l10n` تاريخيًا أثقل
تجربةً لتبديل اللغة أثناء التشغيل (Runtime) مقارنة بحزم مثل `easy_localization`. القرار المعتمَد يقبل
هذا التعقيد الإضافي الطفيف في التنفيذ **مقابل** تجنّب أي تبعية خارجية لميزة جوهرية — مفاضلة واعية،
موثَّقة هنا حتى لا تُنسى لاحقًا عند التصميم الفعلي لتدفّق "تبديل اللغة" في شاشة الإعدادات.

| **fpdart** | مكتبة Functional Programming كاملة (Monads/Lenses) — قوة زائدة عن حاجة Result Pattern بسيط. |
| **hive** / **isar** (الأصليتان) | مهجورتان فعليًا (مستودع isar الأصلي أُرشِف مارس 2026) — `drift` البديل الأصحّ صيانةً عند الحاجة لاحقًا. |
| **camera** (الحزمة المخصّصة) | لبناء واجهة كاميرا كاملة مخصّصة — المتطلبات تستبعد أي تحرير وسائط داخل التطبيق، فهذا مبالغة واضحة؛ `image_picker` يكفي. |
| **ffmpeg_kit_flutter** | **متوقفة رسميًا** — الشركة المطوِّرة (Arthenica) أعلنت تقاعدها في 6 يناير 2025، شارة "discontinued" صريحة على pub.dev. |
| **dio_smart_retry** | منطق إعادة المحاولة يحتاج قواعد أعمال خاصة (401/500/429/Timeout/Upload) لا توفّرها أي حزمة عامة — يُكتَب كـ Interceptor مخصّص. |
| **easy_localization** | `gen-l10n` الرسمي من Flutter مُفضَّل — رسمي، أخف، بلا تبعية إضافية، أنسب لمشروع طويل الأمد (`slang` مرفوضة لنفس السبب). |

## ✅ خلاصة الاعتماد

**Package Baseline معتمَد ونهائي** بتاريخ 2026-08-01 — 16 حزمة Required، 6 حزمة Recommended، البقية

واحد، وتخضع بالكامل لمبدأ `00-VISION-AND-SCOPE.md` §٢: **الـ Backend مصدر الحقيقة الوحيد، وFlutter
عميل ذكي لا يكرّر منطق أعمال**. هذا المستند هو المرجع الرسمي لأي قرار حزمة لاحق — لا حاجة لإعادة فتح
هذه المقارنات عند بدء مرحلة الـ Architecture إلا إذا ظهر متطلب جديد لم يكن معروفًا وقت هذا الاعتماد.
